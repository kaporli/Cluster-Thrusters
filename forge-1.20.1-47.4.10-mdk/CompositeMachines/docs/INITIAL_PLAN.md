# Composite Machines — Mekanism multiblock addon (PoC: Composite Smelter)

## Context

The Cluster-Thrusters modpack uses Mekanism, where every machine is a single "magic" block. The user wants a custom addon mod that makes machines Create-style *composed* multiblocks instead. PoC: a **Composite Smelter** — a flexible hollow cuboid (3x3x3 up to 9x9x9) built from Mekanism Steel Casing / Structural Glass walls, with exactly one **Smelter Core** in a wall, ≥1 **Heating Unit** inside, and item/energy **port blocks** anywhere in the walls. Bigger structure + more heaters = faster + more parallel smelting.

User decisions (confirmed):
- **Shape**: flexible cuboid 3x3x3..9x9x9, hollow, core in wall, heaters inside, ports in walls; size scales speed/parallelism.
- **Engine**: our own formation logic (beacon/Create-tank style) — do NOT extend Mekanism's internal `TileEntityMultiblock` framework.
- **Blocks**: reuse `mekanism:steel_casing` + `mekanism:structural_glass` for walls; new custom blocks: Smelter Core, Heating Unit, Item Input Port, Item Output Port, Energy Port.
- **Recipes/energy**: powered via Forge Energy; smelts everything Mekanism's Energized Smelter can (`mekanism:smelting` + vanilla furnace recipes); works with Mekanism universal cables + logistical transporters.

New standalone subproject following the existing pattern of `TrashSlotQuarkCompat/` and `RelicsCompatKeybind/` (own gradle wrapper + settings.gradle, NOT in root build). Mod: **"Composite Machines"**, modid `compositemachines`, folder `forge-1.20.1-47.4.10-mdk/CompositeMachines/`.

## Verified facts (checked via javap against `Mekanism-1.20.1-10.4.16.80.jar` and live web)

- Recipe lookup: `MekanismRecipeType.SMELTING.getInputCache().findFirstRecipe(level, stack)` → `ItemStackToItemStackRecipe` (`getOutput(input)`, `test(stack)`). Confirmed in bytecode that SMELTING wraps all vanilla `RecipeType.SMELTING` recipes too — one lookup covers everything. Server-side only.
- Mekanism universal cables natively accept plain Forge Energy (`IEnergyStorage`) — no Mekanism energy API needed. Logistical transporters use `IItemHandler`.
- ModMaven hosts the exact version: `mekanism:Mekanism:1.20.1-10.4.16.80` at `https://modmaven.dev/` (no classifier = full jar; needed since `mekanism.common.*` recipe classes aren't in the `-api` jar).
- Mekanism is MIT — recoloring its textures is legal (we'll generate our own programmer-art anyway).
- Tuning baselines from Mekanism config: Energized Smelter = 50 J/t ≈ 20 FE/t, 200 ticks/op.
- Existing subprojects' build.gradles use hardcoded `C:/Users/Elias/...` paths — new mod must NOT (use ModMaven; local-file `fg.deobf(files('../../.minecraft/mods/Mekanism-...jar'))` kept as commented fallback).

## Implementation steps (each leaves a compiling jar)

### M0 — Scaffolding
- Copy `gradlew`, `gradlew.bat`, `gradle/` from `TrashSlotQuarkCompat/`.
- `settings.gradle`: `rootProject.name = 'compositemachines'`.
- `build.gradle`: group `com.compositemachines`, archive `composite-machines`, version `0.1.0`, `minecraft 'net.minecraftforge:forge:1.20.1-47.4.10'`, official mappings 1.20.1, Java 17, `jar.finalizedBy('reobfJar')`, ModMaven repo + `implementation fg.deobf('mekanism:Mekanism:1.20.1-10.4.16.80')`, plus:
  ```groovy
  tasks.register('deployJar', Copy) {
      dependsOn 'build'
      from jar.archiveFile
      into '../../.minecraft/mods'
  }
  ```
- `src/main/resources/META-INF/mods.toml`: modid `compositemachines`, dep on `mekanism [10.4,)` AFTER BOTH, forge `[47,)`, minecraft `[1.20.1,1.21)`.
- `pack.mcmeta` (pack_format 15), entry class `com/compositemachines/CompositeMachinesMod.java` (`@Mod`, wires DeferredRegisters).
- Verify: `./gradlew build` produces jar.

### M1 — Registration + assets
- `registry/CMBlocks.java`: `smelter_core` (`SmelterCoreBlock`, HORIZONTAL `FACING` + `FORMED` props), `heating_unit` (plain Block, **no BE** — counted by scan, breakage caught by revalidation), 3 ports via one `PortBlock` class + `PortType` enum (`FORMED` prop, `onRemove` notifies core).
- `registry/CMBlockEntities.java`: `SmelterCoreBlockEntity` type; **one** `PortBlockEntity` type registered for all 3 port blocks.
- `registry/CMItems.java` (BlockItems), `registry/CMCreativeTab.java`.
- Assets (`assets/compositemachines/`): blockstates, models (`orientable` core, `cube_all` others), `lang/en_us.json`, 16x16 programmer-art textures generated by `CompositeMachines/tools/gen_textures.py` (Pillow): steel-grey base, orange core face, glowing heater, arrow ports, `_formed` brighter variants.
- Data: loot tables (drop self), wall tag `data/compositemachines/tags/blocks/smelter_wall.json` = `[mekanism:steel_casing, mekanism:structural_glass, our 3 ports]` (core checked separately to enforce exactly-one).

### M2 — Formation engine (`com/compositemachines/multiblock/`)
- `SmelterStructure.java`: formed-structure record — `min/max` BlockPos, heating count, port positions, NBT helpers.
- `FormationResult.java`: success(structure) / failure(message, pos).
- `SmelterFormationValidator.java` (pure static, testable):
  1. Seed: `core.relative(facing.getOpposite())` must be interior, else "Core must face outward".
  2. Bounds: walk 6 axes from seed through interior (air/heating unit) up to 7 steps until wall-tag/core/port hit → min/max; fail with direction if none.
  3. Hull: every hull cell ∈ `#compositemachines:smelter_wall` or the core (count cores = exactly 1); interior cells = air or heating unit (count). Failures name block + BlockPos.
  4. Constraints: dims 3..9, heaters ≥ 1, ports only in hull, port not linked to a different formed core.
- Trigger: `SmelterCoreBlock.use()` server-side empty hand — unformed → validate (success/fail message to player); formed → chat status line (size, heaters, parallel ops, FE, active ops). **No GUI for PoC** — chat status; all state lives in one BE so a screen is a clean later milestone.
- On form: core BE persists structure, sets `FORMED=true` on self + ports, writes `corePos` into each `PortBlockEntity`, invalidates port LazyOptionals.
- Unform: port broken → notifies core; core broken → clears its ports; **Mekanism casing/glass broken (no hook possible)** → core revalidates stored bounds every 20 ticks while formed (cheap ≤729 reads, skip unless `level.hasChunksAt`) → unform with position, reset states, invalidate caps. Buffers stay in core; spill only when core itself is destroyed.

### M3 — Smelting tick (`blockentity/SmelterCoreBlockEntity.java`)
- State: `ItemStackHandler inputSlots(9)`, `outputSlots(9)`, `EnergyStorage` (capacity `100_000 + 50_000*heaters`, receive 10_000/t), per-slot `progress[]`, structure, formed. Full NBT.
- `SmelterTuning.java`: `BASE_TICKS=200`, `FE_PER_TICK_PER_OP=20`, `parallelOps = min(9, heaters + interiorVolume/27)`, `ticksPerOp = max(20, 200 / (1 + (heaters-1)/2.0))`.
- Server ticker: 20-tick revalidation; per input slot up to parallelOps: lookup via `MekanismRecipeType.SMELTING.getInputCache().findFirstRecipe(level, stack)` (cached per slot by input item; **isolated in one class `SmeltingRecipeLookup.java`** — only place touching `mekanism.common.*`), check output fits (`ItemHandlerHelper.insertItemStacked` simulate), extract 20 FE/t, advance progress; at ticksPerOp consume input (shrink 1), insert output. Output full → stall holding progress.

### M4 — Port capabilities (`blockentity/PortBlockEntity.java` + `capability/`)
- `corePos` (NBT) + LazyOptional. `getCapability`: INPUT → insert-only `IItemHandler` view of core inputs; OUTPUT → extract-only view of outputs; ENERGY → receive-only `IEnergyStorage` delegate. Wrappers in `capability/PortItemHandler.java`, `PortEnergyHandler.java` (delegate via `Supplier<SmelterCoreBlockEntity>`, behave empty when core missing/unformed).
- Unformed (`corePos == null`) → `LazyOptional.empty()`. Invalidate on form/unform/unload so cables/transporters re-query.
- FE-only is sufficient for universal cables (verified); optional `IStrictEnergyHandler` exposure is a noted ~40-line follow-up, skipped for PoC.

### M5 — Crafting recipes (`data/compositemachines/recipes/`)
Shaped, steel via `#forge:ingots/steel`:
- Core: S R S / S F S / S R S (R=redstone, F=furnace).
- Heating Unit: S B S / B M B / S B S (B=blaze powder, M=magma block).
- Input port: steel ring + hopper center; Output port: steel ring + dropper; Energy port: steel ring + redstone block.

### M6 — Build, deploy, verify
1. `cd CompositeMachines && ./gradlew deployJar` → jar lands in `.minecraft/mods/`.
2. Launch Cluster-Thrusters in PrismLauncher (macOS).
3. Creative: build hollow 3x3x3 (casing walls, core in wall facing out, heater in the 1 interior cell, swap in 3 ports). Right-click core → formed message. Negative tests: missing corner, stone in wall, no heater, core facing into wall → precise error w/ position.
4. Ultimate Energy Cube → universal cable → energy port; chest+logistical transporter → input port; output port → transporter → chest. Smelt iron ore; verify FE drain via core status.
5. Test a Mekanism-only recipe (iron dust → ingot) to prove `mekanism:smelting` coverage.
6. Break a casing mid-smelt → unform within 1s, cables disconnect.

## Risks & mitigations
- `mekanism.common.*` recipe classes are internal (verified against exactly 10.4.16.80) → all such calls isolated in `SmeltingRecipeLookup.java`; documented fallback: query vanilla RecipeManager for both `minecraft:smelting` and `mekanism:smelting` types (`MekanismRecipeType` IS a vanilla `RecipeType`, verified).
- ModMaven down → commented local-file fg.deobf fallback in build.gradle.
- fg.deobf chokes on full Mekanism jar → switch to `:api` classifier for compile + reflection-free vanilla-RecipeManager fallback, or local-file dep.
- Structural glass belongs to Mekanism's own multiblock system → it's just a blockstate in our tag; if Mekanism's validator ever interferes, drop glass from the wall tag (data-only).
- Heater/casing breakage detection delayed up to 1s (20-tick revalidation) → acceptable for PoC; capability wrappers re-check formed per call so no dupes.
