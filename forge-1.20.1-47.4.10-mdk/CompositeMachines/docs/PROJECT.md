# Composite Machines — Project Notes

Living document: the original idea, every decision made, current state, and where to take it
next. Written 2026-06-11 after the Composite Smelter PoC shipped (v0.1.0).

## The vision (original idea)

> A Mekanism "addon" mod that allows you to build Create-like multiblocks. Instead of Mekanism
> being all magic 1-block machines, you have to **compose** machine blocks. Start with the
> smelter as a PoC: instead of a single Energized Smelter, build a multiblock structure out of
> steel casing, a burning unit, input/output ports, an energy port, a cauldron unit, a chimney —
> with a very basic smelter possible from just a burning unit & cauldron.

The user's first sketch (a vertical tower):

```
         Exhaust
            ↑
      ┌─────────┐
      │ Glass   │
      │ Chamber │
HV ───│ Smelter │─── HV
      │  Core   │
      │Heating  │
      ├─────────┤
      │ Furnace │
      │ Base    │
      └─────────┘
```

The end-state dream: every Mekanism machine type gets a composed-multiblock counterpart, making
machine building a Create-like spatial/creative activity instead of placing one block.

## Decisions made (user-confirmed — don't re-ask)

| Question | Decision |
|---|---|
| Structure shape | **Flexible cuboid 3x3x3..9x9x9** (not the fixed tower, not fixed 3x3x3). Hollow; exactly 1 Smelter Core in a wall; ≥1 Heating Unit inside; ports anywhere in walls. Size scales speed & parallelism. |
| Formation engine | **Our own logic** (beacon/Create-tank style). Explicitly NOT Mekanism's internal `TileEntityMultiblock` framework. |
| Blocks | **Mix**: reuse `mekanism:steel_casing` + `mekanism:structural_glass` for walls (via block tag), custom functional blocks (core, heater, 3 ports). |
| Recipes & energy | **Forge Energy** in; smelts **everything Mekanism's Energized Smelter can**; must work with all Mekanism pipes (universal cables = FE natively, logistical transporters = IItemHandler). |
| GUI | None for the PoC — chat status on right-click. A real GUI is a planned follow-up. |

## Current state (v0.2.0 — shipped & load-verified)

- v0.1.0: core mechanics — user confirmed formation/smelting/pipes **work in-game**.
- v0.2.0 "fancy pass": container GUI (3x3 in / 3x3 out, energy gauge, progress arrow, ops
  counter) replaces the chat status; core + heaters get a `lit` blockstate while smelting with
  glowing textures, light, flame/smoke/lava particles and crackle sounds (visible through
  structural glass); item ports are 3D framed models with recessed holes on all faces
  (`tools/gen_port_models.py`); GUI texture generated by `tools/gen_gui.py` (slot coordinates
  must stay in sync with `SmelterMenu`/`SmelterScreen`).
- GUI sync note: energy values exceed the 16-bit ContainerData limit, so they're split into
  15-bit LO/HI pairs (see `SmelterMenu.DATA_*` and the `menuData` in the core BE).
- Old-save note: pre-0.2.0 structure NBT lacks heater positions; the 20-tick revalidation
  rebuilds it automatically within a second of loading.

### Architecture map

| File | Role |
|---|---|
| `multiblock/SmelterFormationValidator` | Pure-static structure validation: seed → bounds walk → hull/interior scan → constraints. Precise error messages with offending positions. |
| `multiblock/SmelterStructure` | Immutable formed-structure record (bounds, heater count, port positions) + NBT. |
| `blockentity/SmelterCoreBlockEntity` | ALL machine state: 9 input + 9 output slots, energy, per-slot progress, structure; server tick; 20-tick revalidation; form/unform; chat status. |
| `blockentity/PortBlockEntity` | Stateless proxy: stores `corePos`, exposes capabilities, invalidates LazyOptionals on form/unform. |
| `capability/PortItemHandler` / `PortEnergyHandler` | Insert-only / extract-only / receive-only views onto the core's buffers. |
| `machine/SmeltingRecipeLookup` | THE ONLY `mekanism.common.*` consumer (recipe cache). Fallback documented in-class. |
| `machine/SmelterTuning` | Every balance number: 20 FE/t/op, 200 base ticks, parallelOps = min(9, heaters + volume/27), ticksPerOp = max(20, 200/(1+(heaters-1)/2)). |
| `machine/MachineEnergyStorage` | FE storage, receive-only externally, internal `consume()`, resizable capacity. |

Verified-from-jar API facts (Mekanism 1.20.1-10.4.16.80, via `javap`):
- `MekanismRecipeType.SMELTING.getInputCache().findFirstRecipe(level, stack)` → `ItemStackToItemStackRecipe`; `.getOutput(input)`, `.getInput().getNeededAmount(input)`, `.containsInput(level, stack)`.
- The SMELTING cache wraps all vanilla `RecipeType.SMELTING` recipes — one lookup covers everything. Server-side only.
- Universal cables accept plain `IEnergyStorage` (FE) — no Mekanism energy API needed.

## Roadmap / ideas for next sessions

Near-term polish (smelter):
1. ~~GUI for the core~~ — DONE in 0.2.0.
2. ~~Active visuals/particles~~ — DONE in 0.2.0 (lit states + particles + sounds).
3. **Exhaust/chimney block** — original sketch had one. Could be cosmetic (smoke particles while
   active) or functional (required on top, or vents = +speed).
4. Formation/unformation sound + particles (the moment of forming is still silent).
5. 3D model + recessed socket for the **energy port** too (item ports got theirs in 0.2.0).
6. Expose `IStrictEnergyHandler` on the energy port (~40 lines, only needed if a pack
   disables Mekanism's FE integration).
7. JEI/EMI integration: show the structure layout & block recipes.
8. Optionally: make Heating Units consume something (lava/blaze fuel) or run hotter near them.

The bigger vision (one machine type at a time, reusing the formation engine):
- **Composite Crusher / Enrichment Chamber** — same shape grammar, different core + recipe type
  (`MekanismRecipeType.CRUSHING` / `ENRICHING` — both are `SingleItem` caches, identical lookup
  code; consider generalizing `SmelterCoreBlockEntity` into an abstract
  `ComposedMachineCoreBlockEntity` keyed by recipe type before adding the second machine).
- **Fluid ports** for machines with fluid I/O.
- Multi-core machines / shared walls between adjacent composed machines.
- Config file for tuning (sizes, FE rates) instead of constants.
- Disable/hide the vanilla Mekanism single-block machines in the pack (CraftTweaker/KubeJS side)
  once composed versions are good enough — that's the "no more magic 1-block machines" endgame.

## Gotchas learned the hard way

- Gradle 8.8 dies on system Java 25 ("class file major version 69") — `gradle.properties` pins
  Temurin 22. The foojay plugin auto-downloads the Java 17 compile toolchain.
- `cp -R` of `gradlew` can drop the execute bit — `chmod +x gradlew` if "permission denied".
- The two sibling subprojects (`TrashSlotQuarkCompat`, `RelicsCompatKeybind`) still carry
  hardcoded `C:/Users/Elias/...` dependency paths and no java-home pin — they will NOT build on
  this Mac as-is. Use this project's build.gradle as the template for any new subproject.
- Pack quirk (from memory): on macOS the pack freezes unless Better Tags + itlt are disabled and
  `-Djava.awt.headless=true` is set in the instance JVM args.
